the problem

Features add complexity.
Complexity slows us down.

Traditional development is linear. Every sprint makes the codebase a little harder to understand, a little more fragile, a little less fun.

🔄

Same bugs, different sprint. We fix the same class of issues over and over because the fix never taught the system anything.

🧠

Knowledge lives in heads. How to do X, why Y works that way, what not to touch in Z — all tribal, all fragile.

🏗

Context rebuilding. Every new task starts with re-learning the area. "Wait, how does this service work again?"

📉

Linear throughput. 10 sprints of effort produces 10 sprints of output. Never more. Often less.

💡
The question: What if every task you completed made the next task faster? Not linearly — exponentially?

phase 1

Plan: Fix bugs on paper
before they reach prod.

Research the codebase. Study existing patterns. Design the approach. Identify every file you'll touch. The plan is the deliverable.

🔎

Research first

Let AI scan the codebase, read framework docs, and surface similar implementations. You provide judgment — it provides coverage.

🗺

Map the blast radius

Every file that will change. Every test that needs updating. Every downstream effect. Know the shape of the work before writing line one.

phase 2

Work: Monitor,
don't micromanage.

AI implements the plan step-by-step in an isolated worktree. You supervise at the milestone level, not the keystroke level.

🌳

Isolated worktrees

In-flight work is untouched. Feature develops in a clean branch with zero conflict risk.

✅

Continuous validation

Tests, linters, type checkers run after every change. Catch drift immediately, not at PR time.

🏗

Architect, not typist

Your value is in the what and why. The how is increasingly handled by tools.

🎯
The shift: You wouldn't hand-cut every board when building a house. You'd design the blueprint and operate the tools. Same energy.

Three questions for every AI output

1

“What was the hardest decision here?”

Reveals tricky areas and judgment calls.

2

“What alternatives did you reject?”

Shows the option space and reasoning.

3

“What are you least confident about?”

Gets AI to surface its own weaknesses.

💡 Human review shifts to intent, approach, and business logic. Automated agents handle syntax, style, and security.
phase 4 — the key differentiator

Compound: Solve it once.
Teach the system forever.

After every task, extract what you learned into a form the system can reuse. CLAUDE.md entries, skills, agent instructions, solution docs. This is what creates exponential returns.

📚

Solution docs

Write up the problem, root cause, and fix with YAML frontmatter. Next time someone hits the same issue, the system finds it automatically.

📝

CLAUDE.md updates

Naming conventions, error handling patterns, gotchas — codify your taste so AI applies it without being told.

🎫

Skills & agents

Reusable prompt modules that teach Claude domain-specific workflows. Write once, invoke everywhere.

🔍

Verification

After compounding, verify: would the system catch this issue next time? If not, keep refining until it would.

“Teach systems; don't do the work yourself.”
adoption stages

Five stages.
We're climbing.

Compound engineering isn't binary. It's a spectrum. Most of us are at Stage 2. The goal is Stage 3 — where the compounding kicks in.

0
Manual Development
No AI assistance. Traditional hand-coding.
1
Chat-Based Assistance
ChatGPT/Claude for snippets. Copy-paste workflow.
2
Agentic + Line-by-Line Review we are here
AI reads files and makes changes. Developer approves every action.
3
Plan-First, PR-Only Review target
Detailed plan → AI implements → human reviews final PR. Compound engineering begins here.
4
Idea to PR
Describe the outcome. Agent handles research, planning, implementation, testing, self-review.
5
Parallel Cloud Execution
Multiple agents on different features simultaneously. Proactive improvements.
📍
The key transition (2 → 3): Stop reviewing individual lines. Start reviewing plans and PRs. Invest in planning details. Let AI research the codebase. Execute and step away from implementation.
mindset shifts

Uncomfortable truths
worth sitting with.

These aren't strawmen. They're real beliefs most of us hold. Letting go of them is the hardest part of this transition — and the most important.

“Code must be manually typed.”

→

Quality matters. Who or what produces the keystrokes doesn't.

“Every line needs my eyes.”

→

Automated systems catch categories of issues humans miss (and vice versa).

“First attempts should be good.”

→

Expect 95% garbage on attempt one. 50% on attempt two. That's the process.

“More typing = more learning.”

→

Understanding > muscle memory. Reading, reviewing, and designing teach more than typing.

🧘
This is a process. Nobody flips a switch. Start by noticing which beliefs create friction, then experiment with loosening one at a time.
new defaults

What to build into
your workflow.

🧬

Extract taste into systems

Your naming conventions, error handling preferences, testing patterns — put them in CLAUDE.md, skills, and agent instructions. Don't repeat yourself across reviews.

⚖

The 50/50 rule

50% shipping features, 50% improving the system that ships features. System improvements compound; raw feature work doesn't.

🛡

Trust through safety nets

Build guardrails (tests, automated review, monitoring) instead of reviewing every line. Guardrails scale; your attention doesn't.

🤖

Agent-native environments

Can the agent run tests? Create PRs? Read logs? Take screenshots? The more the agent can do, the more you can delegate.

🚀
Parallelization: Compute is the bottleneck now, not human attention. Run multiple review agents simultaneously. Let one agent research while another implements. Think in parallel.

your next steps

Four things to try
this week.

1

Compound one thing

Pick a problem you solved this week. Write a CLAUDE.md entry or a skill for it. Future-you will thank present-you.

2

Ask the 3 questions

Next time you review AI output: hardest decision? rejected alternatives? least confident? See what surfaces.

3

Plan before you build

Before your next feature, write the plan first. Let Claude research the codebase and suggest the approach. Review the plan, then execute.

4

Ask the compound question

After every task: “Will this make the next task easier?” If not, you're shipping features. If yes, you're compounding.

💡 None of this requires new tooling. It's a shift in when you think (before coding) and what you leave behind (knowledge for the system).
