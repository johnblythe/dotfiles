# Demo Best Practices

## Purpose
Demos make work visible. They celebrate progress, align stakeholders, and create accountability.

## What Makes a Great Demo

**It's crisp**
- Don't drone on. Keep it brief.
- 2-5 minutes per demo max
- Context → Demo → Impact

**It's clear**
- Say enough to get the point across — no more
- This is not a lunch and learn; be judicious about which details are salient
- Show, don't tell: live demo > recording > slides > description

**It's customer-focused**
- We have fun, but we're not doing this just for fun — it's for real people
- Always tie work back to the customer: how it eases their pain and makes them the hero
- "Users can now X" not "We refactored Y"

## What to Demo

Good candidates:
- New features (even partial)
- Performance improvements with metrics
- UX/workflow improvements
- Bug fixes with visible user impact
- Automation that saves time
- Dashboards or visualizations
- Developer tooling improvements

Skip:
- Pure refactors with no visible change
- Config changes
- "We're 80% done" without something to show

## Capturing Ideas

Use `/demo <idea>` to log as you go — don't wait until sprint end.

Trigger phrases to watch for:
- "This would be cool to show..."
- "Stakeholders would love this"
- "Big improvement from before"

## Slide Deck Workflow

1. Copy the [Template Slide Deck]
2. Save to shared `ROI > Demos > HS` folder
3. Rename to `YY.MM.DD` based on demo day
4. Add your demos

## Demo Day Prep

- [ ] Each pod has 1-2 demos ready
- [ ] Demo order set (usually by pod)
- [ ] Deck created from template with presenter names
- [ ] Backup plan if live demo fails (screenshot/recording)
- [ ] Clear owner for each demo

## Anti-patterns

| Problem | Fix |
|---------|-----|
| "We have nothing to demo" | Log ideas throughout sprint, not at end |
| 10-minute deep dives | Timebox to 5 min; offer follow-up for interested folks |
| Only showing big features | Small wins count — celebrate incremental progress |
| Demo fails live | Always have a backup recording/screenshot |
