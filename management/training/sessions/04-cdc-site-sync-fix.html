root cause

A 60-second window in a world
that moves in hours.

The CDC worker polls every 5 minutes, but only looks back 60 seconds before its last checkpoint. If Member Admin is slow to propagate, the update is permanently missed.

⏱

The Buffer: 60 seconds

Each poll: last_modified_dt - 60s to now(). After success, checkpoint advances to now().

🏥

Member Admin: hours of delay

Site terminations propagate to the CDC API hours later. By then, the 60s lookback has long since moved past it.

💡
Why the manual fix works: Setting last_modified_dt to an old date forces the window to span all the way back. The sync logic is idempotent — already-synced sites are skipped. So going wider is safe.

step 2 · investigation

Claude reads the service cold.

No prior context about hs-cdc-worker. Claude found the service, read the scheduler, helper, config, and SQL mappers in parallel to trace the full sync mechanism.

~/code/healthsource
Claude
⚡ Reading CDCScheduler.java — polls every 5 min
⚡ Reading CDCServiceHelper.java — builds time window
⚡ Reading application.yml — config defaults
⚡ Reading ConfigDataMapper.xml — SQL for checkpoint
⚡ Reading SiteService.java — idempotency check
 
Found it. The flow:
1. Scheduler fires every 300,000ms (5 min)
2. Window: last_modified_dt - 60s → now()
3. After success: checkpoint advances to now()
4. SiteService skips already-synced sites (idempotent)
 
Buffer is 60 seconds. Upstream delay is hours. That's the bug.
step 3 · the fix

One line. Config, not code.

The buffer was already externalized as a config value. No Java changes needed — just changing the default from 60 seconds to 24 hours.

⚙ services/cdcworker/src/main/resources/application.yml
healthsource:
cdc-worker-scheduler:
site:
enable: ${cdc_worker_site_scheduler_enable:false}
interval: ${cdc_worker_site_scheduler_interval:300000}
- buffer: ${cdc_worker_site_scheduler_buffer:60}
+ buffer: ${cdc_worker_site_scheduler_buffer:86400}
 
# 86400 seconds = 24 hours
# Each 5-min poll now looks back 24h for changes
# Safe: SiteService skips already-synced sites

why it's safe

Wider window, same idempotent logic.

Claude didn't just change a number. It traced the full data flow to verify the change was safe before recommending it.

🔄

Idempotent sync

SiteService compares cdclastmodifieddate — already-synced sites are skipped automatically.

📄

Paginated results

CDC API returns 100 results per page. Wider window = more pages, but pagination handles it.

⚙

Env var override

cdc_worker_site_scheduler_buffer can be tuned per environment without redeploying.

🧠
Key insight: Claude read SiteService.java:69-80 to verify the skip logic before suggesting the wider window. The fix is only safe because the sync is idempotent — and Claude verified that, not assumed it.
takeaways

Patterns worth noticing

💬

Paste the Slack thread

The conversation is the bug report. Claude parses tribal knowledge, names, service references, and prior fixes from natural Slack messages.

🌳

Worktrees (or jj) for safety

In-flight work stays untouched. Git worktrees or jj's native change model — either way, the fix develops in isolation with zero conflict risk.

🔍

Cold-read investigation

Claude had zero context about the CDC worker. It found the service, traced the sync flow across 6 files, and identified the root cause in one pass.

📦

Config over code

The buffer was already externalized. Claude recognized it only needed a default change — no Java modifications, no test changes, minimal risk.
