# Estimation

Estimates are **communication tools**, not commitments.

Help us: prioritize, plan sprints, identify hidden complexity, calibrate over time.

---

## Story Points

Relative complexity, not time.

| Points | Meaning |
|--------|---------|
| 1 | Trivial. Config change. |
| 2 | Small. Well-understood. |
| 3 | Medium. Might hit a snag. |
| 5 | Large. Multiple parts, needs design. |
| 8 | Very large. Probably break it down. |
| 13+ | Too big. Must break down. |

**Why not hours?** Hours feel like commitments, vary by person, miss the point.

---

## Process

**When:** Backlog refinement, not sprint planning.

**How:** Present → Questions → Independent estimate → Reveal simultaneously → Discuss outliers → Converge.

---

## Points Include

Dev time, testing, review cycles, docs, deployment.

## Points Don't Include

External waits, context switching, meetings, PTO. (These affect capacity, not complexity.)

---

## When Wrong

They will be.

1. Communicate early
2. Update ticket with why
3. Adjust scope if possible
4. Learn—what did we miss?

**Don't:** Hide it, work weekends to hit it, blame someone.

---

## Fail Modes

| Mode | Symptom | Fix |
|------|---------|-----|
| Everything's a 1 | Not taking it seriously | Calibrate on reference tickets |
| Anchoring | "They said 5 so I guess 5" | Reveal simultaneously |
| Points = hours | "A 3 is 3 hours" | Relative sizing, not time |
| Never update | Ticket balloons, estimate unchanged | Revise when scope changes |
| Punish misses | Blame game | Misses are learning, not failure |
| Refinement theater | Estimate without understanding | Questions before numbers |
| Velocity worship | "We must hit 40 points" | Velocity is diagnostic, not target |
